# AI 카드 PNG CPU 절감 조사

조사일: 2026-10-02 / 브랜치: `codex/ai-card-automation`

**“근본적 원인 해결을 위해 ms를 줄일 수 있는 방법을 먼저 조사”** 요청 당시의 조사 기록이다. 아래 조사 시점에는 새 배포 없이 누적56장이었다. 이후 승인된 통합 개선·수집 호출 감소·최초 조립 진단을 진행해 현재 원격 누적은88 PNG이며 무료 CPU 조건은 여전히 불충족이다. 최신 로컬 결과는 [조립 함수 분리·native CRC 비교](AI_CARD_AUTOMATION_BLIT.md), 실제 CPU는 [최초 조립·준비 진단](AI_CARD_AUTOMATION_DIAGNOSTIC.md)을 따른다. 아래 미구현·미검증 표현은 조사 당시 상태다.

## 결론

**통합 제안은 글자 파일 읽기·복사 감소 + 800×800 직접 생성 + RLE 압축이다. 720×720을 추가 비교 후보로 둔다.** 각 변경의 효과와 가독성을 따로 확인한 뒤 필요한 것만 결합한다. Worker를 더 나누는 것만으로는 전체 계산량이 줄지 않는다. 해상도 축소는 사용자의 추가 검토 요청에 따라 포함한 후보이며 제품 규격을 이미 변경했다는 뜻은 아니다.

두 병목의 로컬 근거를 확보했다.

1. **글자 준비:** 공통 번들 외에 필요한 글자·스타일 조합은 24~81개인데 3.28~7.61MB의 페이지를 읽는다. 이 글자만 담아 조립기로 넘기는 프레임 묶음은 28.6~89.3KB다. 로컬 workerd 프로파일에서 `readBoundedBody`가 비유휴 self 표본의 **44.1%**를 차지했다. 전체 페이지를 스트림으로 읽고 새 버퍼에 복사하는 구조가 유력한 개선 대상이다.
2. **최종 조립:** 로컬 workerd 프로파일에서 `zlibSync` **47.1%**, `paintText` **11.1%**, PNG 재검증의 JS `crc` **5.6%**였다. 최종 조립은 1,167,480바이트의 전체 화면을 매번 그려 압축한다. 전체 화면 압축·글자 그리기가 다음 대상이다.

이는 **로컬의 원인 후보를 좁힌 결과**다. 마지막 원격 조립 3회의 16/35/29ms를 함수별로 분해한 결과가 아니다. Cloudflare 하드웨어, 새 isolate, JIT, 요청·스트림 경계의 영향을 아직 분리하지 못했으므로 원격 초과 원인을 하나로 확정하지 않는다.

## 1. 측정 기준

- 목표의 ms는 응답 대기시간이 아니라 **CPU 실행 시간**이다. 네트워크 대기는 CPU에 포함되지 않는다. 본문을 JS에서 읽고 복사·검사·압축하는 계산은 줄일 대상이다. Workers Free의 HTTP·Cron CPU 기준은 각각 10ms다. HTTP 200이나 일시적인 한도 초과 허용을 무료 운영 통과로 해석하지 않는다. [Cloudflare 제한](https://developers.cloudflare.com/workers/platform/limits/#cpu-time)
- 운영 Worker의 `performance.now()`는 I/O 없이 CPU 구간을 직접 측정하는 데 적합하지 않다. 이번에는 로컬 workerd와 V8 Inspector를 썼다. 로컬 결과로 실제 운영 CPU를 환산하지 않는다. [공식 CPU 프로파일 방법](https://developers.cloudflare.com/workers/observability/dev-tools/cpu-usage/)
- 압축 비교는 **로컬 경과시간**, Inspector 결과는 **CPU 샘플 비중**, 이전 원격 값은 **Cloudflare invocation CPU**다. 세 종류를 섞어 절감 ms를 계산하지 않는다. startup 55/59ms도 요청 CPU와 구별한다.

## 2. 수행한 로컬 조사

### A. 기존 코드의 CPU 프로파일

`research-profile.mjs`는 기존 `atlas-pipeline-worker.ts`를 그대로 번들링해 로컬 Miniflare/workerd에서 실행한다. 조립 요청 250회(5예제×50), 글자 준비 490회(49개 구간×10)를 샘플링했다. 각 단계 전에 1회 예열한다. 폰트는 미리 읽은 로컬 바인딩으로 제공하며 Cloudflare Static Assets 전송을 재현한 것은 아니다.

| 경로 | 함수               | 비유휴 self 샘플 | 해석                             |
| ---- | ------------------ | ---------------: | -------------------------------- |
| 조립 | `zlibSync`         |  203/431 = 47.1% | 전체 indexed 화면의 Deflate 압축 |
| 조립 | `paintText`        |   48/431 = 11.1% | 글자 픽셀 읽기·색상 변환·그리기  |
| 조립 | `crc`              |    24/431 = 5.6% | 생성된 PNG의 JS CRC 재검사       |
| 조립 | `unpackAtlasChunk` |    20/431 = 4.6% | 프레임 해석·픽셀 검증            |
| 준비 | `readBoundedBody`  |  272/617 = 44.1% | 페이지 본문 읽기·전체 복사       |
| 준비 | `planCardAtlas`    |    36/617 = 5.8% | 매 구간 같은 카드의 배치 재계산  |
| 준비 | `decodeAtlasPage`  |    21/617 = 3.4% | 필요한 글자 해제·검사·묶기       |

비중은 함수 자신의 표본이며 하위 호출을 합친 비중이 아니다. 네이티브 작업이 호출한 JS 함수에 귀속될 수 있다. 표본 수가 적어 작은 차이를 성능 차이로 단정하지 않는다. 최초 진단 실행에서도 조립 압축 46.6%, 준비 본문 읽기 45.9%로 큰 순서는 같았다. 마지막 실행 원자료 요약을 보관했다.

조립 요청 전부 기존 원격 PNG와 바이트가 같았다. 로컬 서버와 Inspector는 `finally`에서 종료했다. 근거: [프로파일 요약](evidence/AI_PNG_WORKERD_PROFILE_RESEARCH_2026-10-02.json). 상세 `.cpuprofile`은 Git 제외 경로 `.automation-png/research-assembly.cpuprofile`, `research-glyphs.cpuprofile`에 있다.

### B. PNG 압축 옵션 비교

기존 원격 PNG 5장의 IDAT을 해제하고 **같은 scanline 바이트**를 다시 압축했다. Node와 로컬 workerd 각각 6옵션×5예제×12라운드×20회 = **7,200회**의 측정 압축을 수행했다. 옵션별 예열 5회, 실행 순서 회전·역순, 압축 해제 후 바이트 일치를 확인했다. PNG 파일 크기는 기존 헤더·팔레트·청크 오버헤드에 새 IDAT 길이를 더한 값이다. 새 압축 PNG의 브라우저 표시 시험은 아직 하지 않았다.

| 예제           | 기존 level 1 | `Z_RLE` | 압축 구간 감소 | 예상 PNG 크기: 기존 → RLE |
| -------------- | -----------: | ------: | -------------: | ------------------------: |
| 표현형         |      0.767ms | 0.696ms |           9.2% |          25,223 → 23,077B |
| 비교형         |      0.846ms | 0.692ms |          18.2% |          23,041 → 20,888B |
| 긴 표현형      |      1.037ms | 0.946ms |           8.8% |          38,211 → 35,396B |
| 긴 비교형      |      0.983ms | 0.917ms |           6.8% |          38,677 → 37,159B |
| 문자 범위 예제 |      1.042ms | 1.017ms |           2.4% |          38,493 → 37,503B |

표는 **로컬 workerd의 예열 후 압축만의 평균 경과시간**이다. 20회 묶음 측정으로 타이머 해상도 영향을 줄였으며 요청별 p95/p99는 아니다. Node에서도 RLE 방향은 같았다. 이번 결과만으로 원격 요청 전체에서 2~18% 줄어든다고 주장하지 않는다.

- `Z_RLE`: 가장 먼저 시험할 저위험 옵션. PNG에 맞춰 반복값을 다루는 전략이며 픽셀 손실이 없다. 다만 이번 절감은 **0.025~0.154ms**라 단독 해결책은 아니다. [zlib 공식 설명](https://www.zlib.net/manual.html#Advanced)
- `Z_HUFFMAN_ONLY`: 3.70~4.21ms로 기존보다 느려 제외한다.
- `Z_FIXED`, `memLevel: 9`: 5예제에서 일관된 개선이 없어 우선하지 않는다.
- `level: 0`: PNG 예상 크기 **1,168,304B**로 앱의 1MiB 제한을 넘는다. 무압축으로 회피하지 않는다.

현재 `node:zlib`는 Cloudflare가 지원하고 네이티브 구현도 확인했다. 이미 네이티브 압축을 쓰므로 “JS 압축을 native로 교체”는 새로운 개선안이 아니다. [Cloudflare zlib](https://developers.cloudflare.com/workers/runtime-apis/nodejs/zlib/), [workerd 구현](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/node/zlib-util.c%2B%2B)

### C. 글자 페이지의 불필요한 읽기 계산

현재 한 페이지는 1,024개 코드포인트 슬롯이다. 실제로 필요한 글자의 압축만 해제하더라도, 읽는 파일은 큰 페이지 전체다.

| 예제           | 필요한 비공통 글자 | 현재 페이지 읽기 | 현재 읽는 바이트 | 최종 프레임 묶음 |
| -------------- | -----------------: | ---------------: | ---------------: | ---------------: |
| 표현형         |                 41 |             22회 |       5,110,786B |          42,520B |
| 비교형         |                 24 |             14회 |       3,418,978B |          28,627B |
| 긴 표현형      |                 41 |             14회 |       3,465,708B |          50,276B |
| 긴 비교형      |                 40 |             13회 |       3,282,532B |          49,525B |
| 문자 범위 예제 |                 81 |             33회 |       7,614,150B |          89,329B |

기존 글자 압축 데이터를 그대로 유지하며 페이지 슬롯 수만 바꾸는 경우를 계산했다. 새 형식 구현이나 CPU 실측은 아니다. 1,024 슬롯 계산은 현재 파일 크기와 정확히 일치하는지 검증했다. 빈 페이지는 생략하고 전체 한글·스타일 지원을 유지한다.

| 슬롯/페이지 | 전체 정적 파일 수(라이선스 포함) | 예제별 읽기 감소 범위 | 페이지 조회 범위 |
| ----------- | -------------------------------: | --------------------: | ---------------: |
| 1,024: 현재 |                              477 |                  기준 |          13~33회 |
| 256         |                            1,667 |            54.5~64.9% |          21~58회 |
| 128         |                            3,231 |            69.7~81.2% |          24~68회 |
| 64          |                            6,291 |            82.6~89.9% |          24~73회 |
| 32          |                           12,377 |            90.9~94.8% |          24~74회 |

**32·64 슬롯이 유력하다. 단, 읽기 바이트 감소율을 CPU 감소율로 해석하면 안 된다.** 조회 횟수가 늘어 API·스트림 비용이 증가한다. 따라서 전체 요청 비용으로 비교해야 한다.

- Free Static Assets 파일 수 20,000 기준에는 두 후보가 들어간다. 실제 산출 파일 수·크기는 빌드 후 다시 확인한다. [Cloudflare 제한](https://developers.cloudflare.com/workers/platform/limits/)
- 기존처럼 작은 페이지 2개마다 Worker를 호출하면 최대 74페이지에서 준비 37회가 되어 안 된다. 3페이지씩 묶으면 이 5예제에서는 준비 25회+수집 1회+조립 1회=27회다. 32 Worker invocation 한도 및 상위 운영 호출의 여유를 함께 계산한다. 이는 예제의 계산이며 일반 입력의 한도 증명이 아니다. [Service Binding 한도](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/#limits)
- 한 Worker에 모든 페이지를 모으는 경우 최대 74조회가 된다. Free subrequest 50/내부 서비스 1,000 규칙과 Static Assets의 실제 집계·호출 체인을 검증해야 한다. 최종 설계 전에 경로별 상한과 과다 입력 거절을 둔다. 파일을 잘게 나누기만 한 후보는 통과로 보지 않는다.
- `Range`로 필요한 바이트만 읽는 대안은 현재 Static Assets 바인딩에서의 동작을 확인하지 못했다. 일반 CDN Range 문서를 이 바인딩의 보장으로 간주하지 않는다.

## 3. 해상도를 포함한 통합 개선안

### 해상도 후보

1080×1080은 앱의 초기 규격이다. 카카오 공식 피드 예제에는 640×640도 사용된다. 아래 수치는 픽셀 개수의 산술 비교이며 카카오 화면의 가독성이나 CPU 절감을 실측한 값은 아니다. [카카오 기본 템플릿](https://developers.kakao.com/docs/ko/message-template/default)

| 해상도      |     픽셀 수 | 1080 대비 픽셀 감소 | 제안                                     |
| ----------- | ----------: | ------------------: | ---------------------------------------- |
| 1080×1080   |   1,166,400 |                기준 | 기존 결과·품질 비교 기준                 |
| 900×900     |     810,000 |               30.6% | 800의 가독성이 부족할 때 중간 후보       |
| **800×800** | **640,000** |           **45.1%** | **우선 비교 후보**                       |
| **720×720** | **518,400** |           **55.6%** | **800과 함께 성능·가독성 비교**          |
| 640×640     |     409,600 |               64.9% | 작은 한글·확대 선명도 확인 전에는 후순위 |

- 처음부터 목표 해상도로 그린다. 1080을 만든 뒤 축소하면 기존 그리기 비용과 축소 비용이 남는다. 사전 글자 자료도 목표 크기로 생성하여 런타임 글자 리사이즈를 피한다.
- 글자·여백의 상대적 크기를 유지하되 작은 한글 획, 긴 비교형, 회색 번역, 모바일 표시와 원본 확대를 확인한다. 800 또는 720의 품질이 충분하다고 아직 단정하지 않는다.
- 픽셀 감소는 전체 CPU 감소와 다르다. 입력 검증·배치·요청 수·직렬화 비용이 남는다. 작은 글자 자료가 읽기 바이트를 얼마나 줄이는지도 다시 측정한다.
- 기존 1080 이미지·예약과의 호환을 유지한다. 새 규격은 PNG 생성, 업로드·복원 검증, 이미지 메타데이터, 카카오 payload의 실제 가로·세로에 일관되게 반영해야 한다.
- **해상도가 다른 PNG 사이에는 픽셀 동일성을 요구하지 않는다.** 같은 해상도에서 글자 페이지·복사·압축만 바꾸는 비교에는 동일 픽셀을 요구한다.

| 3    | 800×800·720×720으로 직접 생성하고 글자 자료도 해당 크기로 준비 | 그리기·압축 대상 픽셀과 글자 자료량 | 작은 한글·긴 비교형·모바일·확대 품질, 기존 1080 이미지·예약 호환               |
| 4    | 최종 Deflate를 `Z_RLE`로 비교                                  | 일반 문자열 매칭                    | 같은 해상도에서 decoded 픽셀 동일성·1MiB·브라우저 표시 검증                    |
| 5    | 신뢰 가능한 내부 생성 경로의 중복 CRC 비용 줄이기              | native CRC 생성 뒤 JS CRC 재계산    | 외부 PNG 업로드 검증은 유지. native CRC로 동일 검증을 유지하는 대안부터 비교   |
| 6    | 카드 배치를 한 번 만들고 구간에 필요한 계획만 전달             | 구간마다 전체 `planCardAtlas` 반복  | 고정 예제 사전 계산으로 성능을 속이지 않음. 입력·버전·범위 검증 유지           |
| 7    | 빌드 시 글자의 비어 있지 않은 가로 구간을 준비                 | 투명 픽셀 검사·반복 색상 변환       | 같은 해상도에서 픽셀 동일성, 여러 색·겹침·경계 확인                            |

**1~4를 각각 측정한 뒤 필요한 것만 결합한다.** 수집기 CPU 초과도 있었으므로 조립기만 빨라졌다고 합격 처리하지 않는다. 페이지 읽기량 감소율·픽셀 감소율·압축 단계 시간 감소율은 서로 다른 지표이며 더하거나 곱해 전체 CPU 절감률로 만들지 않는다.

비교 순서는 다음과 같다. 같은 예제·문장·번호를 쓰고 폰트와 자산을 미리 읽었는지 등 측정 조건도 기록한다.

1. **기준:** 기존 1080·기존 페이지·기존 압축.
2. **원인별 비교:** 작은 페이지, 복사 경로 개선, 800 직접 생성, 720 직접 생성, RLE를 각각 기준과 비교한다. 해상도 비교에 필요한 해당 크기의 글자 자료는 그 후보의 필수 구성으로 포함한다.
3. **통합 후보 A:** 800 + 선택한 작은 페이지 + 복사 개선 + 효과가 확인된 압축 전략.
4. **통합 후보 B:** 720 + 같은 개선. A보다 CPU 여유가 필요한 경우와 품질 차이를 평가한다.
5. 충분한 후보가 있으면 채택하고, 미충족이면 5~7번의 잔여 병목을 프로파일로 확인한다. 무조건 추가 최적화를 모두 구현하지 않는다.

현재 근거는 페이지 읽기량 **계산상 82.6~94.8% 감소**, 해상도 800/720의 픽셀 **45.1%/55.6% 감소**, RLE의 1080 압축 구간 **로컬 경과시간 2.4~18.2% 감소**다. 통합 후보 A/B의 CPU와 작은 해상도의 가독성은 모두 미검증이다.

그 뒤에도 최종 조립이 초과하면, 빈 화면 전체를 매번 스캔하는 범용 압축을 줄이는 **희소한 글자 구간 기반 PNG 인코더**가 구조적 대안이다. 흰 여백 반복을 길이로 표현하고 실제 글자 구간만 처리하는 방식이다. 아직 구현·성능 근거가 없으며 사용자 정의 Deflate는 오류 위험이 커 우선순위가 낮다. 최종 PNG에는 하나의 올바른 zlib 스트림·체크섬이 필요하며 독립 압축 조각을 IDAT에 단순 연결하거나 사전 사전을 쓰면 안 된다. [PNG 압축 규격](https://www.w3.org/TR/png-3/#10Compression)

`libdeflate`도 후순위 비교 후보지만 x86/ARM native 성능 설명을 Workers Wasm의 성능으로 옮길 수 없다. 기존 native zlib보다 빠른지 startup·복사 비용까지 포함해 확인해야 한다. [프로젝트 공식 설명](https://github.com/ebiggers/libdeflate)

## 4. 우선하지 않을 방법

- `Promise.all`, 비동기 API, `waitUntil`, 네트워크 지역 변경: 대기시간·응답 시점은 달라질 수 있지만 필요한 CPU 계산을 없애지는 않는다.
- 동일 로직을 더 많은 Worker로 분할: 기존 실측에서 해결되지 않았고 계획 재계산·프레임 검사·직렬화가 늘어난다.
- 캐시 적중률에 의존: 매일 새 내용의 첫 생성이 핵심이다. warm 캐시는 보조 수단이며 cold 경로를 통과해야 한다.
- 해상도 외에 색상·안티앨리어싱·글자 내용을 동시에 줄이기: 원인 비교와 품질 판단이 어려워진다. 해상도 후보도 가독성 확인 없이 운영 규격으로 확정하지 않는다.
- 검증 삭제·제한 상향·유료 상품: 근본 원인 해결로 인정하지 않는다.

## 5. 다음 검증 순서와 중단 기준

1. 현재 원격 로그 **31개 미수집** 원인을 먼저 관측 가능하게 한다. 기존 수집기는 stderr를 버리고 1MB 버퍼 초과·JSON 오류를 집계하지 않는다. provider sampling 경고, 파서 탈락, 종료 시 잔여 이벤트를 **비밀값 없는 카운터**로 남기고 기대한 invocation과 대조한다. 로그가 부족하면 최대·분위수·통과율을 확정하지 않는다. [실시간 로그의 sampling 한계](https://developers.cloudflare.com/workers/observability/logs/real-time-logs/#limits)
2. 32/64 슬롯·복사 경로·800/720 직접 생성·RLE를 위 순서로 로컬 비교한다. 서로 다른 문장·번호·긴 한글·경계 입력, 준비·수집·조립 전체를 포함한다. 해상도 변경의 품질 확인과 같은 해상도 최적화의 픽셀 동일성 검사를 구분한다.
3. 처음 실행한 isolate와 반복 실행을 나눠 프로파일링한다. 이번 warm 수치를 운영 첫 실행으로 간주하지 않는다. 현재 원격과의 절대 ms 차이도 이 과정에서 조사한다.
4. 모든 품질·호출 상한 검증을 통과한 후보만 별도 원격 시험 대상으로 삼는다. 실제 Free 계정 상태와 승인 범위를 확인하고 모든 단계의 CPU를 수집한다. 이번 조사에서는 배포하지 않았다.
5. 단순한 10ms 근접 대신 여유 있는 실행을 목표로 한다. 내부 목표로 최대 7ms 이하를 잡을 수 있으나 제공사 보장은 아니다. 누락 이벤트 또는 어떤 필수 단계의 반복 초과가 있으면 후속 AI·예약 단계의 무료 적합성은 미완료로 유지한다.

## 재현

이전 시험의 폰트 산출물과 원격 PNG가 `.automation-png/`에 있어야 한다. 없으면 기존 [실측 보고서](AI_CARD_AUTOMATION_FEASIBILITY.md)의 로컬 준비 절차를 따른다. 아래 명령은 로컬 진단만 수행한다.

```powershell
node experiments/automation-png/research-compression.mjs
node experiments/automation-png/research-profile.mjs
node experiments/automation-png/research-pages.mjs
```

새 계정 조건이나 Secret은 필요 없다. 실제 AI·카카오·KV/D1 연동, PC 종료 상태, 신규 후보의 무료 CPU 통과는 이번에 검증하지 않았다.

진단 3개 실행, 진단 스크립트 구문 검사, `git diff --check`, `npm run check:free`를 통과했다. `src/`, `migrations/`, 운영 Wrangler 설정은 `origin/master`와 차이가 없다. 무료 구성 검사는 계정 플랜이나 원격 CPU의 재확인을 대신하지 않는다.

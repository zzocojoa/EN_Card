# AI 자동 제작 수량 선택

2026-10-05 `codex/automation-card-quantity`에서 구현했다. 현재 운영에 반영됐다는 기록은 아니다. 배포 상태는 [공통 출시 관리](PRODUCT_MANAGEMENT.md)를 따른다.

## 사용 방식

- AI 자동 제작에서 **하루 제작 수량 1~5장**을 선택하고 설정 저장 → 자동 제작 시작을 누른다. 수량이 없는 기존 설정은 1장이다.
- 각 카드가 작성 → 교차 검토 → 필요하면 한 번 수정 → PNG 저장 → 개별 예약을 거친다. 카드마다 피드 메시지 한 개이며 사진 묶음 전송이 아니다. 제작 기록에 `1/5`처럼 번호와 그날의 전체 수량을 표시한다.
- 제작은 발송 1시간 전부터 한 장씩 진행한다. 준비된 카드만 발송한다. 검토 실패·중복·분량 초과는 해당 카드만 건너뛰며 무료 한도·인증·저장 오류는 전체 자동화를 중단한다. 수신 결과가 불명이면 다른 자동 카드의 발송도 기존 보호에 따라 멈춘다.
- 기존 발송 엔진의 회차 생성·발송 처리 상한을 유지하므로 여러 장은 수 분에 걸쳐 도착할 수 있다. 5장 전부의 정시 제작·도착을 보장하지 않는다.
- 설정 저장은 진행 중 제작과 대기 예약을 중단한다. 오늘 이미 제작을 시작했다면 수량·시각 변경이나 재시작으로 오늘 분량을 추가하지 않는다. 변경한 수량은 다음 제작일부터 사용한다.
- **오늘 한 장 시험**은 일일 수량과 무관하게 1장, KST 하루 한 번이다. 저장된 일일 수량은 그대로이며 시험 종료 후 정규 제작을 자동 재개하지 않는다.

예: 하루 3장을 설정하면 같은 날짜에 1/3·2/3·3/3 기록을 만든다. 2/3이 검토에 실패하면 1/3과 3/3만 예약한다. 같은 날 5장으로 바꿔도 4/5·5/5를 추가하지 않는다.

## 저장·동시 실행 계약

`cards_per_day`는 정수 1~5이고 누락 시 1이다. 숫자 문자열·소수·0·6 이상은 거부한다. D1 0016은 기존 run과 FK를 보존하면서 `item_index`, `item_count`를 기본 1로 추가한다. 일일 `(day,item_index)`는 UNIQUE이며 trial의 일일 UNIQUE는 유지한다.

첫 카드의 run이 해당 날짜의 수량·설정 버전·발송 시각을 고정한다. N개의 run 생성과 다음 일일 시각 이동은 D1 batch 하나로 처리한다. 일부 INSERT가 실패하면 전체를 되돌린다. 늦은 tick은 과거 날짜의 카드를 몰아서 제작하지 않는다. 각 run에는 별도 카드·이미지·예약·AI 시도·검토 해시·claim이 있어 재시도 시 성공한 다른 카드를 다시 만들지 않는다.

한 tick에서 기존과 같이 한 run의 한 단계만 처리한다. 같은 날짜의 앞 카드가 끝나거나 건너뛰어야 다음 카드를 시작한다. AI relay에는 수량을 보내지 않아 기존 한 장짜리 strict 계약과 호환되며, 카드별 요청·검토·이미지 크기 상한도 유지한다.

## 내부 구조와 리팩토링 검증

2026-10-05 후속 리팩토링에서 `src/automation/run-queue.ts`로 만료 처리, 일일 묶음 생성, 다음 작업 claim, 유휴 상태의 완료 판정을 분리했다. `engine.ts`는 설정 확인 → 만료 → 일일 생성 → claim → AI/이미지/예약 단계 실행의 순서를 담당한다. 기존 SQL 28개와 바인딩 순서·batch 경계·설정 버전/claim 보호를 유지한다. 일일 생성과 다음 시각 이동은 계속 하나의 batch이며 새 DB 조회나 마이그레이션을 추가하지 않았다.

`types.ts`의 `AUTOMATION_TIMING`에는 준비 60분, 제작 마감 여유 5분, claim 2분, 이미지 전파 대기 2분, AI 재시도 1분을 정의한다. claim과 이미지 대기는 값이 같아도 목적이 다르므로 별도 항목으로 유지한다. 설정 시작과 일일 생성은 준비 시간을, 일일 생성과 추가 시험은 제작 마감 여유를 공유하며 실제 값은 바꾸지 않았다. 예약 단계에서 같은 설정을 두 번 파싱하던 부분은 한 번으로 줄였다.

유지보수 예: 시간 정책을 수정할 때는 `AUTOMATION_TIMING`과 사용자 안내를 함께 검토하고, `automation-quantity.test.ts`의 준비 시작 1ms 전/정각 및 제작 마감 1ms 전/정각 검사를 실행한다. 이 검사는 정책 상수를 그대로 가져와 기대값을 계산하지 않고 기존 사용자 동작을 고정한다.

이번 리팩토링 검증은 **4파일 78개 통과**다. 수량 27개(시간 경계 3개 추가)·제품 43개·이미지 RPC 7개와 별도 제품 DO 1개를 실행했다. DO 검사는 로컬 workerd·D1/KV에서 실제 1080 PNG 생성/검증/저장을 확인하며 실제 AI·카카오 발송은 아니다. 타입·Prettier·웹 빌드·세 Worker dry-run·무료 구성 검사도 통과했다. DO dry-run은 런타임 테스트 준비 단계에서 실행했다. 로그는 `backups/automation-quantity-refactor-{tests,runtime,build,free}.log`다.

하루단어 화면 원본 해시와 릴레이 원본/메모리 재빌드 결과가 기존 생성물과 같아 재내보내기는 필요하지 않았다. UI·API·스키마·배포 설정·의존성 변경은 없다. 위 검증은 커밋 전 로컬 변경을 대상으로 수행했으며, 후속 커밋·PR 상태는 [공통 출시 관리](PRODUCT_MANAGEMENT.md)를 따른다. 앞선 PR 커밋의 리뷰/CI를 이 리팩토링의 검증으로 표시하지 않는다. 원격 CPU·실제 다중 수신은 여전히 별도 검증이다.

## 비용과 검증 범위

5장 상한은 앱의 보호 설정이다. 제공사가 5장 무료를 보장하는 값이 아니다. 재시도 없는 정상 5장은 작성 5회·검토 5회·PNG 5개·발송 5회를 사용한다. 검토 후 수정·재시도는 호출량을 늘리며 제공자·단계별 기존 시도 상한, 발송 일일 20회(재시도 포함), 저장 한도를 유지한다. 한도 오류에서 유료 경로로 우회하지 않는다.

2026-10-05 공식 문서에서 [Workers Free CPU 10ms](https://developers.cloudflare.com/workers/platform/limits/)와 [SQLite Durable Objects Free 및 초과 시 실패](https://developers.cloudflare.com/durable-objects/platform/pricing/)를 확인했다. 무거운 제작은 기존 DO에 두고 일반 Worker에 일괄 생성 루프를 추가하지 않는다. [Gemini 한도는 프로젝트·모델별이며 AI Studio에서 확인](https://ai.google.dev/gemini-api/docs/rate-limits)하고, [Groq 한도](https://console.groq.com/docs/rate-limits)도 공유 사용량과 토큰량을 함께 확인해야 한다. 이번 로컬 구현에서 새 AI/Kakao 호출·원격 CPU 측정·계정 변경은 하지 않는다.

## 검증·배포·복구 절차

로컬 D1/KV와 모의 AI·발송으로 1·3·5장, 기존 설정/0015 이력 보존, 동시 최초 생성, 중간 INSERT 실패의 전체 롤백, 재시작/수량 변경의 당일 보충 차단, 추가 시험 1장, 중복·한도·부분 성공을 검증한다. 브라우저 검사는 Chromium/WebKit 및 iPhone 에뮬레이션이며 실제 iPhone 확인과 구분한다.

초기 구현 검증의 전체 **42파일 605개**가 통과했다. TypeScript 34파일 562개(`--exclude 'tests/**/*.test.mjs' --file-parallelism --maxWorkers 2`)와 런타임 8파일 43개를 별도 새 프로세스로 실행했으며 수량 회귀 21개를 포함한다. `npm run build`의 타입·웹·세 Worker dry-run과 `check:free`도 통과했다. 초기 전체 실행은 수정 작업과 겹쳐 600개 통과/5개 실패였고, 새 프로세스 결과와 구분한다. 초기 브라우저 검사의 수량 선택자 5개 실패는 접근성 역할 기반 선택자로 수정한 뒤 38개 모두 재검증했다. 로컬 근거는 `backups/automation-quantity-{final-ts,final-runtime,e2e,build,free}.log`다. 앞서 사용자가 확인한 Workers Free 기록은 보존하되 이번에는 계정과 실제 다중 제작 CPU를 재조회하지 않았다.

`review`의 데이터·API·보안·성능·유지보수·테스트·디자인 검토와 독립 적대적 검토를 수행했다. 동시 Cron 또는 이전 카드의 결과 불명 때문에 다음 자동 카드가 영구 `blocked`로 남는 결함을 발견했다. 회귀 4개가 수정 전 실패하는 것을 확인한 후, 유효한 자동화의 미발송 카드를 `retry_wait`로 돌려 기존 취소·15분 만료 검사를 따르게 수정했다. 원래 `unknown`은 자동 재발송하지 않으며, 사용자의 수신 확인·종료·명시적 재시도 후 남은 카드만 계속한다. 15분이 지나면 미발송 카드만 `missed`가 된다. 수정 후 수량 검증 20개와 별도 만료 회귀 1개, 독립 재검토가 통과했다. 초기 동시 생성·부분 성공의 테스트 보완과 0016 복구 문서 지적도 반영했다. 같은 모델의 독립 문맥 검토이며 기존 CLI 비호환을 교차 모델 검토 성공으로 집계하지 않는다.

화면 검증 38개와 하루단어 생성물의 서버/프록시 19개·타입·변경 QA 파일 lint·제품 빌드가 통과했다. 하루단어 통합 QA도 두 브라우저에서 기본 1장 → 3장 저장 → 저장 실패 재시도 → 5장 초안 → 일시정지/화면 이동/새로고침을 검증했고, 320/390/1440px × 글자 100/200%의 접근성 위반은 0개다. Windows의 Sites 빌드 helper는 npm shim 경로 오류로 실패해, 저장소의 동일한 `node scripts/run-framework.mjs build`를 직접 실행하여 통과했다. 운영 DB·계정·설정·키·예약과 새 실제 AI/카카오 호출은 변경하지 않았다.

커밋 전 추가 검토에서 자동 카드의 결과 불명 대기가 별도 수동 예약까지 15분 지연시키는 결함을 재현했다. 자동 발송 장벽이 있는 자동 카드를 claim 후보에서 제외하여 공용 처리 슬롯을 점유하지 않게 했다. claim 이후의 경합은 기존 DB trigger와 `retry_wait` 반환으로 보호하고 다른 예약 처리는 계속한다. 3장·5장과 1분 뒤 수동 예약의 회귀 두 개가 수정 전 실패했으며, claim 이후 결과 불명 경합·예산 보존 검사도 추가했다. 회차 생성의 기존 tick당 2예약 제한은 유지하며, 이 회귀는 자동 카드 회차를 먼저 준비해 발송 후보 선택을 따로 검증한다. 구형 DB 이력 재현용 테스트 도구는 0014 이전에만 새 자동화 SQL 절을 제외하고 마이그레이션 뒤 원래 조건을 검사한다. 현재 스키마 검사는 원본 SQL 그대로 실행한다. 독립 재검토에서 추가 문제는 없었고 로컬 SQLite 실행 계획은 기존 상태·예약 연결 인덱스를 사용했다. 원격 D1 CPU를 측정한 결과는 아니다.

2. 수량 지원 DO → 비공개 발송 Worker → 주 Worker 순서로 반영한다. 발송 Worker에도 다중 카드의 동시 실행 대기 수정이 포함되므로 생략하지 않는다. 기존 화면의 수량 없는 요청도 1장으로 처리한다. 원본의 확정 커밋을 정식 exporter로 하루단어 작업 브랜치에 내보내고 화면·서버 릴레이 명세를 검증한 뒤 기존 Site에 게시한다. 카드 원본·하루단어 PR 및 실제 배포 상태를 각각 기록한다.
3. 새 설정이나 다중 카드 기록이 생긴 뒤에는 **수량을 지원하는 코드로만 복귀**한다. 이전 DO는 `cards_per_day`를 거부하므로 단순 구버전 rollback을 하지 않는다. 장애 시 자동화를 중단하고 0016 호환 수정본으로 복구한다. 운영 DB를 과거 백업으로 덮어쓰거나 immutable run 설정·시도 이력을 재작성하지 않는다.
4. 실제 다중 카드 제작·수신·일반 Worker CPU는 별도 허용된 시험으로 검증한다. 로컬 모의 발송 통과를 실제 카카오 수신으로 표시하지 않는다.

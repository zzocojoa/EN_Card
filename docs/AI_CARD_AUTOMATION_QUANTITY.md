## 품질 불합격 추가 수정 — 0020 운영

초안과 첫 수정본이 모두 품질 검토에서 탈락하면 **반대 제공자가 한 번 더 수정**한다. 총 수정은 최대2회(revision1→2→3)이며 최종 작성자와 다른 제공자의 독립 검토를 다시 통과해야 PNG·예약을 만든다. 예: Google 초안 → Groq 불합격 → Google 첫 수정 → Groq 불합격 → Groq 추가 수정 → Google 통과 → PNG·예약. 품질 실패를 통과로 바꾸거나 새 run을 만들어 수량을 채우지 않는다.

- 제공자별 단계/차수3회 제한을 유지하며, 모든 단계·차수·제공자를 합쳐 **카드당 총24회**의 명시적 상한을 추가한다. 실패·중복·`started` 상태의 예약 호출도 포함하고 SQL 예약에서 원자적으로 제한한다. 기존 예산을 초기화하지 않는다. 상한/잔여 호출 부족은 `ai_limit`으로 종료한다. 5장 회차의 이론적 상한은120회이며 실제 무료 잔여량을 보장하지 않는다. quota·auth·config·storage 중단 정책은 유지한다.

배포 순서는 유휴·동일 설정 확인 → 쓰기/Cron 차단·진행 호출 종료 → 암호화 백업 →0020 전체 원자 적용·기존 행/FK 대조 →0020 호환 DO 100% 확인 →정식 exporter 화면 게시 →쓰기/Cron 복원이다. 0019 인덱스만 적용할 때의 무중단 예외를 사용하지 않는다. 복구는0020 제약과 이력을 유지하는 호환 코드로 한다. 구 DO는 수정 결과 차수를2로 고정하므로 추가 수정/차수3이 진행 중인 상태에서 구버전으로 되돌리지 않는다. 과거 DB 복원이나 차수/시도 초기화로 우회하지 않는다.

## 수정 제공자 대체 — 0020에서도 유지

- 수정(`revise`)의 현재 제공자가 해당 차수에서3회 시도를 소진하면 반대 제공자의 같은 단계/차수 잔여 시도를 확인한다. 남아 있으면 작성자·검토자를 함께 교체하고 다음 Cron에서 원래 카드·검토 지적을 사용해 수정한다. Google→Groq와 Groq→Google을 모두 지원한다. 초안의 기존 Google→Groq 정책은 유지한다.
- 시도 기록은 삭제하거나 초기화하지 않는다. 한 수정 차수의 호출 상한은 제공자당3회, 두 제공자 합계최대6회다. 성공했지만 중복인 후보와 응답 불명으로 시작만 기록된 호출도 예산에 포함한다. 반대 제공자 예산까지 소진하면 `unavailable`로 종료하므로 반복 전환하지 않는다. 실제 한도 오류(`quota`)·인증·설정 오류는 기존처럼 전체 자동화를 중단한다.
- 대체 수정이 성공하면 기존 검토 결과/검토 해시를 비우고 다음 revision을 **새 작성자와 다른 제공자**가 검토한다. 검토 자체가 실패했다고 작성자에게 자기 검토를 시키지 않는다. 품질 기준 미달은 위의 추가 수정 조건을 평가하고 최종 불합격은 `review_failed`, 검토 호출 예산 소진은 `unavailable`로 종료하며 검토 없이 PNG·예약을 만들지 않는다.
- run/카드/이미지/예약 ID, 중복 거절3회, 최대2회의 수정 차수, claim·설정 version·제작 마감, 기존 발송/저장 보호를 유지한다. 이미 종료된 슬롯을 되살리거나 같은 날 부족 수량을 보충하지 않는다.
- **추가 시험 이력:** 10월6일09:49 시험은 당시40분 제작창에서4장 수신·1장 이미지 대기 후 마감으로 종료됐다. 현재 새5장 시험은 정규와 같은55분 제작창이지만 실제5장 성공을 보장하지 않는다. 이전 실패 회차는 재실행하지 않는다.
- 한 장 추가 시험은 발송15분 전 시작·5분 전 마감으로 실제 제작창이10분이다. 수정3회 실패 후 대체·새 검토·PNG·전파 대기를 모두 끝내기에는 부족하다. 수정 대체의 실제 검증은 정규 제작창과 구별해 계획해야 하며, 추가 시험의 준비창 확장은 별도 변경이다.

예: Google 초안 → Groq 검토에서 번역 수정 요청 → Google 수정503이3회 → Groq 수정 성공 → Google의 새 검토 통과 → PNG·예약. 마지막 Google 검토가 실패하면 전송하지 않는다.

추가 의존성·모델·Secret·DB 마이그레이션·화면/릴레이 API 변경은 없다. 운영 반영 대상은 자동화 DO의 실행 코드이며, 배포 전 현재 진행 중 작업·버전·무료 계정 조건을 확인한다. 변경 후 생성된 시도도 기존0018 스키마에서 읽을 수 있다. 이전 호환 코드로 복귀하면 아직 수정 중인 카드에 새 대체 정책을 적용하지 못할 수 있으므로 원본 시도/역할/이력을 재작성하지 않는다. 배포·실제 재생성/수정 대체·현재 버전 CPU·5장 수신은 로컬 검증과 구분한다.

로컬 회귀: `node node_modules/vitest/vitest.mjs run tests/automation-revise-fallback.test.ts tests/automation-duplicate-retry.test.ts --file-parallelism --maxWorkers 2`. 무료 공유 한도는 [Gemini 프로젝트별 한도](https://ai.google.dev/gemini-api/docs/rate-limits)와 [Groq 한도](https://console.groq.com/docs/rate-limits)를2026-10-06 다시 확인했다. 대체 시도만큼 호출량이 늘 수 있고 실제 계정의 잔여량을 코드로 보장하지 않는다.

실제 검증에서는 **최종 작성자와 최초 초안 작성자가 다를 수 있음**을 반영한다. 예전 `verify-daily.mjs`의 `draft_successes`(현재 writer의 초안 성공만 집계)는 그대로 쓰면 정상 대체 수정을 검토 실패로 오판한다. 배포 후 검증기는 최종 차수의 작성/수정 성공과 반대 제공자의 검토 성공·내용 해시 일치를 함께 확인해야 한다. revision2는 수정(revise의 시도 차수1) 또는 렌더 중복 이후 새 초안(draft의 차수2)으로 만들어질 수 있다. 아래 읽기 SQL은0020의 revision3도 지원한다:

```sql
SELECT r.id, r.revision, r.writer, r.reviewer,
  EXISTS(SELECT 1 FROM automation_attempts t
    WHERE t.run_id=r.id AND t.provider=r.writer AND t.outcome='ok'
      AND ((t.stage='draft' AND t.revision=r.revision)
        OR (r.revision>1 AND t.stage='revise' AND t.revision=r.revision-1))) AS final_write_ok,
  EXISTS(SELECT 1 FROM automation_attempts t
    WHERE t.run_id=r.id AND t.provider=r.reviewer AND t.outcome='ok'
      AND t.stage='review' AND t.revision=r.revision) AS final_review_ok,
  (r.writer!=r.reviewer AND r.content_hash IS NOT NULL
    AND r.content_hash=r.review_hash) AS independent_review_matches
FROM automation_runs r WHERE r.day=? AND r.kind=?;
```

위 확인에 최종 review의 모든 기준 통과, 표현 비중복, 카드/asset 버전·PNG·live 접수·진행 중/결과 불명 없음 및 사용자 실제 수신을 추가 대조한다. 시도 성공만으로 품질·수신을 확인하지 않는다. 배포 후 Git 제외 `backups/automation-quality-rollout-20261006/verify.mjs`에 이 조건과 제공자별 수정 시도 관측을 적용했고 운영 읽기 쿼리를 실행했다. 제작 전0개 조회는 성공 판정이 아니다. 정규5장은10월7일06:30 제작·07:25 마감·07:30 발송 예정이며07:50에 실제 결과를 확인한다.

## 사용 방식 — 현재 운영0020

- AI 자동 제작에서 **하루 제작 수량 1~5장**을 선택하고 설정 저장 → 자동 제작 시작을 누른다. 수량이 없는 기존 설정은 1장이다.
- 각 카드가 작성 → 교차 검토 → 필요하면 최대 두 번 수정 → PNG 저장 → 개별 예약을 거친다. 카드마다 피드 메시지 한 개이며 사진 묶음 전송이 아니다. 제작 기록에 `1/5`처럼 번호와 그날의 전체 수량을 표시한다.
- 제작은 발송 1시간 전부터 한 장씩 진행한다. 준비된 카드만 발송한다. 중복은 같은 자리에서 다른 표현으로 재작성하고 새 후보도 독립 검토한다. 중복 3회·검토 실패·분량 초과는 해당 카드만 건너뛰며 무료 한도·인증·저장 오류는 전체 자동화를 중단한다. 수신 결과가 불명이면 다른 자동 카드의 발송도 기존 보호에 따라 멈춘다.
- 기존 발송 엔진의 회차 생성·발송 처리 상한을 유지하므로 여러 장은 수 분에 걸쳐 도착할 수 있다. 5장 전부의 정시 제작·도착을 보장하지 않는다.
- 설정 저장은 진행 중 제작과 대기 예약을 중단한다. 오늘 이미 제작을 시작했다면 수량·시각 변경이나 재시작으로 오늘 분량을 추가하지 않는다. 변경한 수량은 다음 제작일부터 사용한다.
- **오늘 새 AI 카드 시험**은 일일 수량과 별도로 1~5장, KST 하루 한 번이다. 오늘 발송 시각을 지정하거나 비워서 가장 빠른 시간을 선택한다. 저장된 일일 설정은 그대로이며 시험 종료 후 정규 제작을 자동 재개하지 않는다.

예: 하루 3장을 설정하면 같은 날짜에 1/3·2/3·3/3 기록을 만든다. 2/3이 검토에 실패하면 1/3과 3/3만 예약한다. 같은 날 5장으로 바꿔도 4/5·5/5를 추가하지 않는다.

## 중복 표현 재생성 — 0018

- 기존 카드 전체와 표현 예약에서 중복을 확인하면 해당 run의 `rejected_expressions`에 보존하고 다음 Cron에서 재작성한다. 원래 run ID·카드 번호·수량·시도 기록을 유지하며 새로운 일일/시험 슬롯을 만들지 않는다. 거절한 표현을 최근 카드 목록보다 먼저 AI의 회피 목록에 넣고 요청은 기존 최대 50개를 유지한다.
- 중복을 최대 3회 확인하면 `duplicate_limit`으로 종료한다(최초 중복 뒤 두 번 대체 가능). 기존 제공자별 단계/수정 차수별 시도 상한도 그대로 적용되므로 오류가 섞이면 더 일찍 중단할 수 있다. 중복 대기는 `duplicate_retry`로 표시한다. 이력 원문을 로그나 공개 응답에 추가하지 않는다.
- 재작성한 초안은 새 독립 검토를 거친다. 수정 단계는 원래 카드와 검토 지적을 유지한다. 렌더 시점의 경합으로 중복이 확정되면 검토 해시를 지우고 새 초안부터 검토하며, 이미 생성·수정된 카드/이미지는 덮어쓰지 않는다. 수정 차수와 렌더 횟수도 초기화하지 않는다.
- 0018 최초 배포에서 한 장 시험은 최소25분, 여러 장은 `수량 × 8 + 5분`이었다(2장21분·3장29분·4장37분·5장45분). 기본6틱에 초안 중복 재시도2틱을 포함했다. 위 후속 후보는5장만60분으로 늘린다. 렌더 경합·AI 장애·교정이 겹치거나 Cron이 지연되면 마감될 수 있으며, 무한 재생성·정시5장 성공을 보장하지 않는다.
- 최초0018 예: 5장을21:30에 시험하면20:45부터 제작하고21:25에 마감했다. 2/5의 첫 후보가 중복이면2/5 안에서 다시 작성한다. 이전에 이미 `skipped`/`expired`로 종료된 시험은 자동으로 되살리지 않는다.

배포 전 쓰기/Cron 차단과 암호화 백업 → 0018 적용 → 기존 열/행·attempt 참조·FK 대조 → 0018 호환 DO → 화면 반영 순서다. 서버의 최신 마이그레이션 없이 새 코드를 먼저 가동하지 않는다. 복구 시 자동 제작을 중지하고 0018 호환 수정본을 사용하며, 거절/시도 이력을 지우거나 과거 DB 백업으로 운영 이력을 덮어쓰지 않는다. 기존 실행의 고정된 마감/시각은 수정하지 않는다.

재현: `npm test -- tests/automation-duplicate-retry.test.ts tests/automation-trial-quantity.test.ts`. 원격 검증과 새 5장 시험은 별도 단계이며 이번 수정만으로 기존 시험을 성공 처리하지 않는다.

## 새 AI 여러 장 추가 시험 — 2026-10-05의 0017 구현·배포 이력

`codex/automation-multi-trial`은 오늘 이미 정규 제작을 마친 경우에도 그 이력을 수정하지 않고 별도의 새 AI 1~5장 시험을 한 번 등록한다. `POST /api/automation/trial`의 기존 `{version}` 요청은 계속 1장이다. 새 요청은 `{version,trial:{cards:5,due_at:발송UTC밀리초}}`이며 `due_at`은 선택이다. 저장된 주제·난이도·양식을 사용하고 별도의 settings 입력은 거부한다. 시험 슬롯 전부와 활성화는 D1 batch 하나로 처리하며 중단 후 수량을 보충하지 않는다.

한 장은 기존 25분 뒤 발송·발송 15분 전 제작을 유지한다. 여러 장은 최소 `카드 수×6+5분` 전에 등록·제작하고 발송 5분 전에 마감한다. **5장은 최소 35분 준비**다. 매분 Cron, 렌더 종료 후 KV 전파 대기와 순차 제작 시간을 포함한 보호 값이며 제공사 지연·수정·검토 실패로 일부 카드가 건너뛰어질 수 있다. 날짜는 실제 KST 당일, 시각은 분 단위만 허용한다.

검증: 기존 제품/수량 70개, 신규 시험 11개와 실제 로컬 DO 1080 PNG/API 입력 1개, Chromium/WebKit 화면 2개, 하루단어 프록시/릴레이 19개와 타입·빌드·무료 구성 검사. `review`의 전문·독립 적대적 검토가 준비창 부족을 지적해 5장 처리창을 25→30분으로 수정했다. 회귀는 렌더 1초 경과와 고정 분 단위 Cron으로 5장 전부의 이미지·예약·모의 1회 발송을 확인한다. 보조 Codex CLI는 설치 버전과 모델 비호환으로 실패하여 교차 모델 검토로 집계하지 않는다.

운영 0017 적용 전 쓰기/Cron 정지·DPAPI 암호화 백업을 수행했고 적용 후 기존 모든 데이터 행의 해시·FK 오류 0을 확인했다. DO/주 Worker를 갱신했고 기존 발송 Worker·바인딩·Cron·Free 구성은 보존했다. 이번 실제 새 5장 수신과 부하 CPU는 별도 시험 결과를 따르며 로컬 성공으로 대체하지 않는다. 장애 시 시험을 일시정지하고 **0017 호환 코드**로 복구하며 기존 run/attempt를 삭제하거나 수량을 다시 채우지 않는다.

재현: `npm test -- tests/automation-trial-quantity.test.ts tests/automation-product-do.test.mjs`, `npm run test:e2e -- tests/e2e/redesign.spec.ts --grep "자동 제작"`. 이미 적용한 원격 마이그레이션은 반복하지 않는다.

첫 카드의 run이 해당 날짜의 수량·설정 버전·발송 시각을 고정한다. N개의 run 생성과 다음 일일 시각 이동은 D1 batch 하나로 처리한다. 일부 INSERT가 실패하면 전체를 되돌린다. 늦은 tick은 과거 날짜의 카드를 몰아서 제작하지 않는다. 각 run에는 별도 카드·이미지·예약·AI 시도·검토 해시·claim이 있어 재시도 시 성공한 다른 카드를 다시 만들지 않는다.

한 tick에서 기존과 같이 한 run의 한 단계만 처리한다. 같은 날짜의 앞 카드가 끝나거나 건너뛰어야 다음 카드를 시작한다. AI relay에는 수량을 보내지 않아 기존 한 장짜리 strict 계약과 호환되며, 카드별 요청·검토·이미지 크기 상한도 유지한다.

## 내부 구조와 리팩토링 검증

2026-10-05 후속 리팩토링에서 `src/automation/run-queue.ts`로 만료 처리, 일일 묶음 생성, 다음 작업 claim, 유휴 상태의 완료 판정을 분리했다. `engine.ts`는 설정 확인 → 만료 → 일일 생성 → claim → AI/이미지/예약 단계 실행의 순서를 담당한다. 기존 SQL 28개와 바인딩 순서·batch 경계·설정 버전/claim 보호를 유지한다. 일일 생성과 다음 시각 이동은 계속 하나의 batch이며 새 DB 조회나 마이그레이션을 추가하지 않았다.

`types.ts`의 `AUTOMATION_TIMING`에는 준비 60분, 제작 마감 여유 5분, claim 2분, 이미지 전파 대기 2분, AI 재시도 1분을 정의한다. claim과 이미지 대기는 값이 같아도 목적이 다르므로 별도 항목으로 유지한다. 설정 시작과 일일 생성은 준비 시간을, 일일 생성과 추가 시험은 제작 마감 여유를 공유하며 실제 값은 바꾸지 않았다. 예약 단계에서 같은 설정을 두 번 파싱하던 부분은 한 번으로 줄였다.

유지보수 예: 시간 정책을 수정할 때는 `AUTOMATION_TIMING`과 사용자 안내를 함께 검토하고, `automation-quantity.test.ts`의 준비 시작 1ms 전/정각 및 제작 마감 1ms 전/정각 검사를 실행한다. 이 검사는 정책 상수를 그대로 가져와 기대값을 계산하지 않고 기존 사용자 동작을 고정한다.

이번 리팩토링 검증은 **4파일 78개 통과**다. 수량 27개(시간 경계 3개 추가)·제품 43개·이미지 RPC 7개와 별도 제품 DO 1개를 실행했다. DO 검사는 로컬 workerd·D1/KV에서 실제 1080 PNG 생성/검증/저장을 확인하며 실제 AI·카카오 발송은 아니다. 타입·Prettier·웹 빌드·세 Worker dry-run·무료 구성 검사도 통과했다. DO dry-run은 런타임 테스트 준비 단계에서 실행했다. 로그는 `backups/automation-quantity-refactor-{tests,runtime,build,free}.log`다.

하루단어 화면 원본 해시와 릴레이 원본/메모리 재빌드 결과가 기존 생성물과 같아 재내보내기는 필요하지 않았다. UI·API·스키마·배포 설정·의존성 변경은 없다. 위 검증은 커밋 전 로컬 변경을 대상으로 수행했으며, 후속 커밋·PR 상태는 [공통 출시 관리](PRODUCT_MANAGEMENT.md)를 따른다. 앞선 PR 커밋의 리뷰/CI를 이 리팩토링의 검증으로 표시하지 않는다. 원격 CPU·실제 다중 수신은 여전히 별도 검증이다.

## 비용과 검증 범위

5장 상한은 앱의 보호 설정이다. 제공사가 5장 무료를 보장하는 값이 아니다. 재시도 없는 정상 5장은 작성 5회·검토 5회·PNG 5개·발송 5회를 사용한다. 검토 후 수정·재시도는 호출량을 늘리며 제공자·단계별 기존 시도 상한, 발송 일일 20회(재시도 포함), 저장 한도를 유지한다. 한도 오류에서 유료 경로로 우회하지 않는다.

2026-10-05 공식 문서에서 [Workers Free CPU 10ms](https://developers.cloudflare.com/workers/platform/limits/)와 [SQLite Durable Objects Free 및 초과 시 실패](https://developers.cloudflare.com/durable-objects/platform/pricing/)를 확인했다. 무거운 제작은 기존 DO에 두고 일반 Worker에 일괄 생성 루프를 추가하지 않는다. [Gemini 한도는 프로젝트·모델별이며 AI Studio에서 확인](https://ai.google.dev/gemini-api/docs/rate-limits)하고, [Groq 한도](https://console.groq.com/docs/rate-limits)도 공유 사용량과 토큰량을 함께 확인해야 한다. 이번 로컬 구현에서 새 AI/Kakao 호출·원격 CPU 측정·계정 변경은 하지 않는다.

초기 구현 검증의 전체 **42파일 605개**가 통과했다. TypeScript 34파일 562개(`--exclude 'tests/**/*.test.mjs' --file-parallelism --maxWorkers 2`)와 런타임 8파일 43개를 별도 새 프로세스로 실행했으며 수량 회귀 21개를 포함한다. `npm run build`의 타입·웹·세 Worker dry-run과 `check:free`도 통과했다. 초기 전체 실행은 수정 작업과 겹쳐 600개 통과/5개 실패였고, 새 프로세스 결과와 구분한다. 초기 브라우저 검사의 수량 선택자 5개 실패는 접근성 역할 기반 선택자로 수정한 뒤 38개 모두 재검증했다. 로컬 근거는 `backups/automation-quantity-{final-ts,final-runtime,e2e,build,free}.log`다. 앞서 사용자가 확인한 Workers Free 기록은 보존하되 이번에는 계정과 실제 다중 제작 CPU를 재조회하지 않았다.

`review`의 데이터·API·보안·성능·유지보수·테스트·디자인 검토와 독립 적대적 검토를 수행했다. 동시 Cron 또는 이전 카드의 결과 불명 때문에 다음 자동 카드가 영구 `blocked`로 남는 결함을 발견했다. 회귀 4개가 수정 전 실패하는 것을 확인한 후, 유효한 자동화의 미발송 카드를 `retry_wait`로 돌려 기존 취소·15분 만료 검사를 따르게 수정했다. 원래 `unknown`은 자동 재발송하지 않으며, 사용자의 수신 확인·종료·명시적 재시도 후 남은 카드만 계속한다. 15분이 지나면 미발송 카드만 `missed`가 된다. 수정 후 수량 검증 20개와 별도 만료 회귀 1개, 독립 재검토가 통과했다. 초기 동시 생성·부분 성공의 테스트 보완과 0016 복구 문서 지적도 반영했다. 같은 모델의 독립 문맥 검토이며 기존 CLI 비호환을 교차 모델 검토 성공으로 집계하지 않는다.

화면 검증 38개와 하루단어 생성물의 서버/프록시 19개·타입·변경 QA 파일 lint·제품 빌드가 통과했다. 하루단어 통합 QA도 두 브라우저에서 기본 1장 → 3장 저장 → 저장 실패 재시도 → 5장 초안 → 일시정지/화면 이동/새로고침을 검증했고, 320/390/1440px × 글자 100/200%의 접근성 위반은 0개다. Windows의 Sites 빌드 helper는 npm shim 경로 오류로 실패해, 저장소의 동일한 `node scripts/run-framework.mjs build`를 직접 실행하여 통과했다. 운영 DB·계정·설정·키·예약과 새 실제 AI/카카오 호출은 변경하지 않았다.

커밋 전 추가 검토에서 자동 카드의 결과 불명 대기가 별도 수동 예약까지 15분 지연시키는 결함을 재현했다. 자동 발송 장벽이 있는 자동 카드를 claim 후보에서 제외하여 공용 처리 슬롯을 점유하지 않게 했다. claim 이후의 경합은 기존 DB trigger와 `retry_wait` 반환으로 보호하고 다른 예약 처리는 계속한다. 3장·5장과 1분 뒤 수동 예약의 회귀 두 개가 수정 전 실패했으며, claim 이후 결과 불명 경합·예산 보존 검사도 추가했다. 회차 생성의 기존 tick당 2예약 제한은 유지하며, 이 회귀는 자동 카드 회차를 먼저 준비해 발송 후보 선택을 따로 검증한다. 구형 DB 이력 재현용 테스트 도구는 0014 이전에만 새 자동화 SQL 절을 제외하고 마이그레이션 뒤 원래 조건을 검사한다. 현재 스키마 검사는 원본 SQL 그대로 실행한다. 독립 재검토에서 추가 문제는 없었고 로컬 SQLite 실행 계획은 기존 상태·예약 연결 인덱스를 사용했다. 원격 D1 CPU를 측정한 결과는 아니다.

추가 수정 뒤 관련 **19파일 360개**가 통과했다(파일별 최종 결과의 합집합, 수량 회귀 24개 포함). 근거는 `backups/automation-quantity-{ship-regression,ship-related,ship-final}.log`다. 초기 관련 실행의 과거 DB 도구 9개 실패와 회차 생성 상한까지 함께 측정했던 회귀 1개 실패는 위 테스트 도구·시나리오 분리 후 해당 4파일 73개를 다시 실행해 모두 통과했다. 나머지 15파일의 통과 결과를 함께 사용하며 실패했던 실행 전체를 통과로 집계하지 않는다. 타입·웹·세 Worker dry-run·무료 구성도 재검증했다. 화면/릴레이 원본은 이 발송 수정으로 바뀌지 않아 앞선 브라우저·하루단어 검증과 생성물 해시를 유지한다.

1. 로컬 검증 후 [기존 배포 절차](SETUP.md#원격-실행-절차)에 따라 현재 설정·이력과 암호화 백업을 보존한다. 진행 중 제작·발송이 없는지 확인한 후 미적용 D1 마이그레이션을 **0020까지** 순서대로 적용한다. 원칙적으로 쓰기/Cron을 차단하며 0019 인덱스만 적용하는 호환 예외는 설정 문서를 따른다. 기존 행·FK·이력과 각 run의 ID·번호/수량·자식 참조 보존을 대조한다. 이미 적용한 파일은 재실행하지 않으며 수정 제공자 대체 자체에는 추가 마이그레이션이 없다.
2. 수량 지원 DO → 비공개 발송 Worker → 주 Worker 순서로 반영한다. 발송 Worker에도 다중 카드의 동시 실행 대기 수정이 포함되므로 생략하지 않는다. 기존 화면의 수량 없는 요청도 1장으로 처리한다. 원본의 확정 커밋을 정식 exporter로 하루단어 작업 브랜치에 내보내고 화면·서버 릴레이 명세를 검증한 뒤 기존 Site에 게시한다. 카드 원본·하루단어 PR 및 실제 배포 상태를 각각 기록한다.
3. 현재는 **0020 호환 코드로만 복구**한다. 이전 DO는 수량·다중 시험·거절 이력 또는 추가 수정 차수3을 처리하지 못할 수 있으므로 단순 구버전 rollback을 하지 않는다. 운영 DB를 과거 백업으로 덮어쓰거나 immutable run 설정·시도 이력을 재작성하지 않는다. 복구 조건은 [검증 기록](VERIFICATION.md)을 따른다.
4. 실제 다중 카드 제작·수신·일반 Worker CPU는 별도 허용된 시험으로 검증한다. 로컬 모의 발송 통과를 실제 카카오 수신으로 표시하지 않는다.

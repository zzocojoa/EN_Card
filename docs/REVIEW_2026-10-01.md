### R9 — 취소 당시 원인과 현재 일시정지 상태를 구분해야 함

문제 조건은 0008 DB에서 예약 v1의 미발송 카드를 수정으로 취소하고, 같은 이미지를 v2에서 발송한 뒤, 예약이 일시정지된 상태로 0009를 적용하는 경우다. backfill의 `d.error='paused' OR s.reason='paused'`는 현재 예약의 상태만으로 이전 버전의 `error='예약 수정'` 이력도 편입한다. `safe` 판정은 옛 delivery 자체의 호출만 검사한다.

격리된 Node 메모리 SQLite에 실제 0001~0009 SQL을 적용하고 수정하지 않은 `recoveryPreview()`·`decideRecovery()`로 확인했다. 옛 취소 항목은 `safe=1`, `available=true`, ‘확정된 미발송’이 됐으며, 이미 v2에서 `mock_sent`인 동일 asset을 새 예약에 저장했다(`recovered=1`). 잘못된 미결정 항목은 기존 예약 재개도 차단한다. 모의 결과이며 실제 메시지는 보내지 않았다.

수정 제안은 취소 당시 일시정지였음을 입증하는 이력만 backfill하는 것이다. 이미 적용된 0009에는 새 보정 마이그레이션을 추가해 잘못 편입된 **미결정 관계만** 정리하고, 완료된 복구·제외 결정과 발송 이력은 보존한다. 운영 DB에 실제 영향 항목이 있는지는 이번 검토에서 조회하지 않았다.

### R10 — 취소된 예약의 확정 미접수 응답이 영구 대기 상태로 남음

현재 `finish()`는 예약이 `paused`일 때만 거절 결과를 `cancelled`로 정리한다. `sending` 중 사용자가 취소하고 제공사가 403/-402에 해당하는 `reconnect`를 반환하면 delivery는 `blocked`, 예약은 `cancelled`로 남는다.

수정하지 않은 `runEngine()`·`stopSchedule()`·`deleteImage()` 등과 실제 9개 마이그레이션을 메모리 SQLite에서 실행했다. 16분 뒤에도 `blocked`, 모의 호출은 1회였다. 복구 목록은 비었고(`can_resume=false`, `pending_count=0`), 이미지 삭제는 `asset_in_use`, 결과 종료는 `NOT_UNKNOWN`으로 실패했다. 화면은 취소된 예약의 수정·재개·재취소를 제공하지 않는다. 취소 API를 직접 다시 호출하는 우회는 가능하지만 일반 화면에는 해제 경로가 없다.

수정 제안은 현재 예약이 `cancelled`인 경우 확정 미접수 결과를 delivery의 `cancelled`로 종료하되, 원래 거절 결과는 `delivery_attempts`에 보존하는 것이다. 성공·결과 불명·새 인증 버전 보호는 유지하고 일시정지 복구 후보는 만들지 않는다.

### A1 — 세 확인 대화상자의 포커스 격리가 없음

# 운영과 복구

예약 발송의 인증 처리는 기존 비공개 DO의 `credentialToken` RPC에서 수행한다. DO의 `SEND_MODE`는 주 Worker와 같아야 한다. AI만 중지하려면 화면 일시정지 또는 `AUTOMATION_MODE=off`를 사용하고, 수동 발송을 유지할 때는 DO의 `SEND_MODE=live`를 유지한다. DO만 dry_run으로 바꾸면 수동 예약도 인증 대기 후 missed가 될 수 있다. 배포는 RPC를 제공하는 DO를 먼저, 주 Worker를 나중에 적용한다. RPC 통신 실패는 로컬 재갱신으로 우회하지 않는다. 갱신 결과는 기존 D1 잠금·버전·실패 분류를 기준으로 복구한다.

2026-10-04의 이전 갱신 tick CPU 14.004ms 확인 후 위 분리를 적용했다. 같은 날 14:48 KST까지 실제 갱신 DO CPU **6.054ms**, 검증용 주 Worker **2.250ms**를 확인하고 운영 버전을 복원했다. 2.250ms는 정상 예약 엔진 전체 갱신 회차의 측정값이 아니다. 앞선 실제 발송 표본은 주 Worker4.269ms·발송 Worker3.787ms였다. 실제 수신 성공과 CPU 적합성은 별개이며 이 표본을 미래 최댓값으로 보장하지 않는다. [실제 갱신 근거](evidence/AI_TOKEN_REFRESH_VERIFICATION_2026-10-04.json), [무인 제작·발송 근거](evidence/AI_AUTOMATION_TRIAL_2026-10-04.json).

**2026-10-04 14:56 KST 운영 상태:** 영화 대사·초급·표현형 한 장의 10월5일 07:00 제작 시작·08:00 발송을 활성화했다. 종료일도10월5일이다. 그 미래 실행·수신은 아직 검증하지 않았다. [활성화 기록](evidence/AI_AUTOMATION_NEXT_2026-10-05.json).

AI 서버 연결은 기존 Site Secret을 사용한다. 키 오류는 사이트 설정에서 수정하며 DO에 복사하지 않는다. 준비 확인 실패 시 Site의 `0004_card_automation_nonces` 적용과 Google/Groq 키·활성 설정, 기존 bridge/소유자 연결을 확인한다. nonce를 수동으로 삭제하거나 같은 서명으로 AI를 재호출하지 않는다. [전체 구조와 복구 경계](AI_CARD_AUTOMATION_IMPLEMENTATION.md)를 따른다.

## 비공개 발송 Worker 중단·복구

`en-card`의 매분 Cron은 `DELIVERY_SERVICE`로 비공개 `en-card-delivery`의 준비·발송 요청을 호출합니다. 자식에는 공개/preview URL, Cron, KV, 저장된 Secret이 없습니다. 두 Worker는 같은 D1을 사용합니다. 주 Worker의 dry_run 전환만으로 새 실제 발송을 중단할 수 있습니다. 배포 순서는 자식 → 주 Worker이며 자식을 삭제하기 전에 주 Worker의 바인딩을 먼저 정리합니다.

바인딩 오류·불완전한 응답 뒤에는 주 Worker가 직접 재발송하지 않습니다. 자식이 이미 API를 호출했거나 결과를 저장했을 수 있기 때문입니다. 기한이 지난 claimed는 회수하고 sending은 unknown으로 처리합니다. 앱의 시도별 기록과 본인 채팅방을 확인한 뒤 기존 결과 확인 절차를 따르세요.

적용된 스키마와 호환되는 코드의 dry_run 복귀 명령은 다음과 같습니다. 현재 운영0020에는0020 호환 코드를 사용하고, 새 후보0021 적용 후에는 revision4·replacement_origin을 보존하는0021 호환 코드를 사용합니다. `wrangler.deploy.jsonc`와 `wrangler.automation.deploy.jsonc`는 같은 운영 D1·KV·APP_ORIGIN을 가리키고 둘 다 `SEND_MODE=dry_run`이어야 합니다. DO는 off/unconfirmed로 준비합니다. 새 파일은 [설정 절차](SETUP.md#원격-실행-절차)대로 만들며 기존 파일을 덮어쓰지 않습니다. 설정이 바뀌면 로컬 검사부터 다시 실행합니다. 신규 설치 순서와 달리 **긴급 중단은 주 Worker를 먼저 dry_run으로 배포한 뒤 DO 모드를 맞춰** live 주 Worker가 dry_run DO를 호출하는 구간을 피합니다.

```sh
npm run automation:fonts
npx wrangler deploy --dry-run --config wrangler.automation.deploy.jsonc --outdir .worker-automation-build
npx wrangler deploy --dry-run --config wrangler.deploy.jsonc --outdir .worker-build
npm run check:free -- --config wrangler.deploy.jsonc --delivery-config wrangler.delivery.deploy.jsonc --automation-config wrangler.automation.deploy.jsonc --mode dry_run
npx wrangler deploy --config wrangler.deploy.jsonc
npx wrangler deploy --config wrangler.automation.deploy.jsonc
```

DB를 별도 복원 DB로 전환할 때 주 Worker·발송 Worker·DO 세 설정의 D1 식별자를 함께 바꾸고 주 Worker/DO의 KV도 일치시킵니다. 기존 실패·시도·예산을 삭제하거나 자식 장애를 직접 카카오 호출로 우회하지 않습니다. CPU는 일반 Worker와 DO를 각각 관측하며 카카오 응답을 기다린 wall 시간과 구별합니다. 일반 Worker에서 Free 10ms 초과가 관측되면 live 확대를 중단합니다.

## 발송 기록 해석

0010 마이그레이션은 옛 예약 수정의 취소를 일시정지 복구 대상으로 잘못 편입한 미결정 관계만 정리합니다. 적용 전 기존 백업·마이그레이션 이력을 보존하고, 적용 후 FK 검사와 미결정 목록을 확인합니다. 이미 완료된 복구·제외와 대상 예약은 자동으로 되돌리지 않으므로, 기존 복구로 만든 예약은 본인 채팅방과 고정 이미지·호출 이력을 대조해 필요하면 일시정지·취소합니다. 기존 운영 DB에 적용된 0009를 수정하거나 재실행하지 않습니다.

수정 서버는 발송 중 취소 뒤 확정 미접수 거절을 받으면 delivery를 `cancelled`로 종료하고 원래 거절은 시도별 기록에 보존합니다. 이 경우 재시도·일시정지 복구 후보 없이 이미지를 정리할 수 있습니다. 성공과 결과 불명은 기존 결과·이미지 보호 규칙을 따릅니다. 이미 이전 서버에서 생긴 취소 예약의 `blocked`는 새 응답 처리로 자동 변경되지 않습니다. 해당 기록의 거절·취소 상태를 확인한 운영자가 같은 version으로 취소 API를 다시 호출하여 정리하며, `unknown`·`sending`에는 이 절차를 적용하지 않습니다.

`sent` 중 `confirmed_by_user=0`은 카카오 API의 `result_code=0` 확인이며 사용자가 읽었다는 뜻이 아닙니다. 결과 불명을 사용자가 수신 확인한 경우에는 `confirmed_by_user=1`로 구별하고 화면에 **사용자 수신 확인**으로 표시합니다. 이 기록은 API 접수 집계에 포함하지 않습니다. `mock_sent`는 격리 테스트의 모의 성공입니다. `dry_run` 기록은 시간·피드 검증이며 운영 회차, 커서, 발송 예산을 소비하지 않습니다.

결과 불명의 수동 처리는 발송 기록의 **결과 확인**에서 합니다. 수신 확인, 중복 위험을 수락한 재시도, **재전송하지 않고 종료** 중 선택합니다. 종료는 수신 여부를 알 수 없는 채로 추가 전송을 포기하는 선택입니다. 원래 state=unknown과 호출 결과는 남고 resolution=abandoned로 구별됩니다. API 접수·수신 확인 집계에 포함하지 않으며 같은 건을 다시 재시도할 수 없습니다. 선택 기록과 시도 내역을 보존합니다. 다른 요청이 먼저 결과를 처리했으면 충돌을 알리므로 새로고침한 뒤 최신 기록을 확인하세요. **시도별 호출 기록 · 사용자 확인**을 열면 해당 카드의 모든 호출과 확인 기록을 조회합니다. 표시하는 전체 시도 횟수는 수동 재시도 후에도 초기화하지 않습니다. 취소·수정되어 원래 버전이 유효하지 않으면 재시도를 거부합니다. 이전 버전·일시정지·취소 예약도 수신 확인 또는 재전송 없이 종료할 수 있습니다. 취소 예약이 자동 활성화되지는 않습니다.

미해결 unknown 또는 sending이 남아 있으면 재개·버전 변경을 거부하고 발송 기록으로 안내합니다. 일시정지·취소는 허용됩니다. 결과를 처리한 뒤 원하는 예약을 직접 재개하거나 수정하세요. 예약 수정은 새 버전의 카드 목록을 만듭니다. 이전 회차의 미발송 항목만 취소합니다. 시간을 수정할 때 남은 목록의 고정 이미지도 유지할 수 있습니다. 수정 화면을 연 뒤 발송이 진행되면 저장을 거부하므로 새로고침 후 예약 수정을 다시 여세요. 재개는 이미 소비한 카드를 제외하므로 과거 이미지 삭제가 남은 반복 예약을 막지 않습니다. 취소한 예약은 수정·재개 대신 새 예약으로 만듭니다. 늦은 인증 오류나 연결 해제는 사용자의 취소·일시정지 상태를 바꾸지 않습니다. 이미 API에 접수된 메시지는 회수할 수 없습니다. 발송 직전의 재확인 뒤 네트워크 호출 사이까지 DB와 카카오를 하나의 트랜잭션으로 묶을 수는 없으므로 정확히 한 번 도착을 보장하지 않습니다.

## 일시정지한 미발송 카드

일시정지 확인창은 현재 회차에서 빠지는 카드 수·표현 목록을 보여줍니다. 확인 중 발송이 진행될 수 있으므로 중지 완료 후 실제 대상 목록을 다시 보여줍니다. sending·미해결 unknown이 있어도 중지는 가능하지만 결과를 처리하기 전에는 복구·재개를 막습니다.

**미발송 카드 다시 예약**에서 확정된 미발송만 기본 선택합니다. 10장·회차당 5장에서 3장이 접수된 뒤 중지하면 2장이 복구 대상이고 아직 회차에 편입되지 않은 5장은 기존 예약에 남습니다. 선택한 2장은 최소 2분 이후의 새 일회 예약으로 만들고, **남은 5장 예약 재개**를 별도로 눌러 기존 반복 예약을 이어갑니다. 원래 예정 시각이 15분 넘게 지났어도 원본을 되살리거나 즉시 발송하지 않습니다. 회차당 5장을 초과하는 기존 자료는 5장씩 2분 간격의 새 예약으로 나눕니다. 활성 예약 10개와 분당 3건 제한은 그대로 적용되어 실제 발송은 더 늦어질 수 있습니다.

복구하지 않을 카드는 체크를 해제합니다. 복구·제외 수와 제외 목록을 확인하고 확인란에 동의해야 저장됩니다. 제외 결정은 원본 취소 이력에 연결되어 보존되며 자동으로 번복되지 않습니다. 저장 후 원본 카드별 새 예약 ID 또는 제외 결과를 보여줍니다. 복구 예약 자체도 예약 목록에서 수정·중지·취소할 수 있습니다.

누적된 중지 카드가 많으면 복구·제외 합계 40장씩 처리합니다. 화면의 미결정 총량과 이번 목록을 확인하고 **이번 카드 모두 복구/제외** 또는 개별 선택을 사용하세요. 저장하면 다음 목록으로 넘어가며 확인란을 다시 선택해야 합니다. 모든 원본의 선택이 끝날 때까지 기존 예약 재개와 미결정 이미지 삭제는 차단됩니다. 활성 예약 10개 상한으로 복구가 실패하면 해당 묶음 전체를 저장하지 않으므로 기존 복구 예약이 완료되거나 중지된 뒤 재시도하세요.

현재 상태와 전체 호출 이력이 모두 확정된 미발송을 증명해야 복구할 수 있습니다. sent/mock_sent, 사용자 수신 확인, sending, unknown, 재전송 없이 종료한 기록은 자동 편입하지 않습니다. 과거 unknown이나 접수 이력이 남은 cancelled도 안전한 후보가 아닙니다. 이미지를 지웠거나 읽을 수 없으면 사유를 표시하며 조용히 빠뜨리지 않습니다. 제외 후 해당 카드를 다시 작성·검토해 새 예약으로 준비하세요. 원문 수정 뒤에도 원래 고정 이미지가 남으면 그 버전과 payload를 보존합니다.

처리 선택 전 후보의 이미지는 정리에서 보호합니다. 일시정지 후 예약을 취소했더라도 **중지 카드 확인**에서 해당 후보를 복구·제외할 수 있습니다. 취소한 기존 예약과 나머지 목록은 자동 재개되지 않습니다. 새 복구 예약만 명시적 선택으로 만들어집니다. 동시 저장 충돌이 표시되면 새로고침하여 이미 기록된 결과를 확인하세요.

## 과거 연결 해제 복구 이력 보정 — R11

0009는 현재 예약이 일시정지라는 이유로 옛 연결 해제 이력도 복구 관계에 넣을 수 있었고, 0010은 예약 수정 원인만 정리했습니다. 이후 같은 이미지가 정상 발송됐더라도 옛 건이 미발송으로 제시될 수 있습니다. 0011은 이미 적용된 두 파일을 보존하고 일시정지가 아닌 **미결정** 관계만 정리합니다. delivery·실제 호출·예산과 완료된 복구/제외·대상 예약을 지우거나 자동 재발송하지 않습니다.

새 코드의 취소 원인은 `paused`, `cancelled`, `schedule_changed`, `disconnected`로 저장하며 화면용 `error`와 분리합니다. 기존에 확정할 수 없는 원인은 NULL로 보존합니다. 다음 읽기 전용 조회는 0011 적용 후 이미 결정된 비일시정지 이력을 확인합니다. 결과가 있으면 원래 메시지·사용자 결정·대상 예약을 대조한 뒤 필요한 조치를 개별 판단하며 마이그레이션이 선택을 자동으로 되돌리지 않습니다.

```sql
SELECT p.delivery_id,p.decision,p.target_schedule_id
FROM pause_recoveries p JOIN deliveries d ON d.id=p.delivery_id
WHERE p.decision IS NOT NULL
  AND d.cancellation_reason IN ('cancelled','schedule_changed','disconnected');
```

2026-10-01 17:04 KST에 승인 후 백업·쓰기 중단·0011·FK/이력 확인·두 Worker 배포를 완료했습니다. 운영 소스는 6ec4579이며 이력 11개·FK 오류 0, 기존 인증·예약·발송·예산 보존을 확인했습니다. 적용 증거는 [VERIFICATION.md](VERIFICATION.md)의 R11 운영 기록을 따릅니다. 다른 DB를 업그레이드할 때도 [SETUP.md](SETUP.md)의 같은 순서를 지킵니다. 이미 적용된 0011을 다시 실행하거나 취소 원인 쓰기를 지원하지 않는 이전 서버로 돌아가지 않습니다.

## R12~R14 후속 보완의 복구·접속 규칙

아래 규칙은 운영 제품 소스 `b24c2df`(배포 기준 HEAD `bf1726d`)에 적용됩니다. 사용자 승인으로 2026-10-01 18:55 KST에 0012·두 Worker를 반영했습니다. 미적용 0012만 적용하고 12개 이력·FK 오류 0·기존 데이터 보존을 확인했습니다. 적용된 파일을 다시 실행하지 않으며 상세 배포·최신 CPU 결과는 [VERIFICATION.md](VERIFICATION.md)를 따릅니다.

- **원인 불명 과거 취소:** 0012는 미결정 후보의 `cancellation_reason='paused'`를 요구합니다. NULL이나 다른 원인을 일시정지로 추측하지 않습니다. 해당 후보는 복구할 수 없지만 제외할 수 있으며, 결정 전에는 기존 예약 재개·이미지 삭제 보호를 유지합니다. 이미 완료된 결정·대상 예약·원본·호출·예산은 보존합니다.
- **호출 직전 인증 중지:** 같은 예약 버전의 `needs_reconnect` 경합에서 외부 호출이 없고 15분 유예 내이면 카드를 `blocked`로 보존합니다. 재연결 후 해당 예약을 직접 재개하면 같은 회차의 미발송을 이어갑니다. 유예가 지나면 `missed`이며 새 날짜로 준비합니다. 일시정지·취소·연결 해제·버전 교체는 취소 처리와 기존 원인 기록을 유지합니다. 호출 예약 예산은 되돌리지 않습니다.
- **복구 입력 오류:** 열린 복구창 안에서 오류를 확인하고 날짜·시각을 고쳐 다시 저장합니다. 실패 시 카드 선택과 입력은 유지됩니다. 새 선택 묶음으로 넘어가면 다시 확인해야 합니다.
- **OAuth 시작:** 로그인 중 재연결은 운영자 세션과 CSRF를 확인합니다. 로그아웃 후 로그인은 보관한 `SETUP_TOKEN`을 **운영자 등록·접속 토큰**에 입력합니다. 최초 등록도 기존 토큰이 필요합니다. 입장 검증에 실패하면 OAuth 상태 행을 쓰거나 정리하지 않습니다. 이 보완 때문에 기존 Secret을 재발급하지 않습니다.

예를 들어 인증 중지 직전까지 접수된 3장은 그대로 두고, 호출하지 않은 카드만 재연결·직접 재개로 이어갑니다. 제공사 설정 오류·갱신 재시도 소진·결과 불명의 기존 수동 처리 정책은 유지합니다.

## 저장량 정리

연결 및 설정에서 PNG를 백업하고 필요한 이미지만 삭제합니다. 이미지 삭제는 KV 삭제 확인 후 D1의 용량을 반환합니다. 메타데이터는 과거 발송 이력을 위해 남깁니다. 활성·일시정지 예약과 미확정 발송이 참조하는 이미지는 DB에서 삭제를 차단합니다. 중단된 uploading은 5분이 지난 뒤 정리할 수 있습니다. 자동 대량 삭제는 하지 않습니다.

정리 후 업로드가 늦게 끝나면 저장 성공으로 표시하지 않고 해당 파일을 다시 정리합니다. 실패한 파일은 `cleanup_needed` 또는 `deleting` 상태와 예약 용량을 유지하여 설정 화면에서 재시도할 수 있습니다. 반환한 용량을 다른 업로드가 사용했다면 복구 집계가 일시적으로 200MB를 넘을 수 있으며, 정리가 끝나기 전 신규 업로드를 막습니다. KV와 D1의 변경 사이를 하나의 트랜잭션으로 묶는 기능은 아닙니다.

삭제 전 원본 URL의 수명을 고려하세요. 과거 메시지의 링크가 깨질 수 있으며 캐시된 이미지는 당분간 남을 수 있습니다. 로그 보관 기간을 이미지 삭제 기준으로 사용하지 않습니다. 앱의 저장량은 이 앱이 예약한 바이트이며 계정 전체 KV 사용량이 아닙니다.

## 학습 자료 백업·복원

- 보관함의 **JSON 백업**은 카드 내용·ID·revision만 포함하며 토큰·세션은 제외합니다. 가져올 때 ID는 중복 검사에 사용하고 서버가 새 ID를 발급합니다.
- 설정의 **PNG 다운로드**로 이미지를 별도로 보관합니다.
- JSON을 가져온 뒤 해당 카드를 편집하여 새 PNG를 만들거나 **PNG 백업 복원**에서 저장된 PNG를 업로드합니다. 카드 내용과 이미지가 일치하는지 검토해야 예약에 쓸 수 있습니다. 새 asset과 새 URL이 생깁니다.
- 백업은 최대 100개씩 내려받습니다. **다음 JSON 백업** 버튼이 없어질 때까지 파일을 모두 보관하세요. 백업 중에는 카드 편집·가져오기를 멈춰 자료가 바뀌지 않게 합니다. 파일의 next_cursor는 다음 파일을 찾는 메타데이터입니다.
- 가져오기는 파일당 최대 100개·1,000,000바이트입니다. 오류가 있으면 행 번호를 안내하며 해당 파일 전체 저장을 중단합니다. 각 파일은 한 번씩 가져오세요. 여러 파일을 반복해서 가져오면 새 ID의 카드가 추가되므로 이미 복원한 파일을 다시 가져오지 않습니다.
- 보관함·이미지 정리·예약·발송 기록의 **더 불러오기**를 사용하면 100개 이후 자료도 확인할 수 있습니다.

전체 D1 복구용 내보내기는 학습 JSON 백업과 다릅니다. 암호화된 토큰·개인 설정을 포함하므로 암호화된 개인 저장소에만 보관하고 Git에 넣지 않습니다.

전체 백업·마이그레이션·배포의 정확한 명령은 [SETUP.md](SETUP.md#2-기존-db-백업--미적용-마이그레이션)에 있습니다. DB 내보내기에 PNG 바이트는 없으므로 이미지도 별도로 백업합니다. 기존 이미지 URL과 KV namespace를 보존하지 못하면 과거 메시지의 링크는 복구되지 않습니다.

## 운영 중단과 스키마 복구

2026-09-30 최초 본인 시험은 권한 부족(403/-402)·CPU 24ms로 중단했습니다. 새 OAuth 요청의 talk_message 확인과 비공개 HTTP Worker 분리 뒤 실제 수신·원본 링크를 확인했습니다. 2026-10-01 승인된 두 시험에서 정상 토큰 갱신과 PC·Chrome·Codex 종료 후 09:11 이미지·원본 수신을 확인했으며 활성 예약은 0개입니다. 갱신 포함 Cron CPU 14ms는 10ms 목표를 초과해 보완·재측정이 남았습니다. 연결 콜백은 talk_message 확인 후에만 토큰을 저장합니다. 기존 실패 이력·시도 예산과 과거 blocked 카드는 보존합니다. 최신 결과는 [VERIFICATION.md](VERIFICATION.md)를 따릅니다.

최초 배포에는 이전 운영 버전이 없었습니다. 복구는 아래 순서로 Cron 중단·현재 스키마와 호환되는 dry_run 수정본을 사용합니다. 0006의 query 분할 오류는 원본 SQL을 바꾸지 않은 file import로 복구했으며 적용 완료 파일을 다시 실행하지 않습니다. [복구 기록](SETUP.md#windows-마이그레이션-오류-복구-기록)을 참고하세요. 지속 Worker observability는 disabled를 유지하고 실제 시험의 CPU는 비밀정보를 제외한 invocation 메타데이터로 측정했습니다.

1. 앱 접근이 가능하면 관련 예약을 일시정지하고 sending·unknown 기록을 확인합니다. 앱 접근이 어려우면 Cloudflare Dashboard에서 이 Worker의 Cron Trigger를 제거하여 새 실행을 중지합니다. 진행 중 외부 호출까지 취소되는 것은 아니므로 접수 여부를 확인합니다. 로그아웃은 발송 중지 수단이 아닙니다.
2. [현재 dry_run 복구 절차](#비공개-발송-worker-중단복구)에 따라 주 Worker와 DO의 대응 설정을 로컬 검사합니다. `npm run check:free -- --config wrangler.deploy.jsonc --delivery-config wrangler.delivery.deploy.jsonc --automation-config wrangler.automation.deploy.jsonc --mode dry_run` 후 주 Worker, DO 순서로 배포하면 Cron이 복원되어도 실제 제작·발송은 중지됩니다. Worker 버전만 되돌리는 rollback은 이전 live 설정을 다시 켤 수 있으므로 무조건 실행하지 않습니다. 연결 해제는 토큰까지 제거하므로 필요할 때만 사용합니다.
3. 쓰기를 멈춘 상태에서 장애 시점 DB를 별도로 export하고 KV·기존 Secret·배포 버전·마이그레이션 이력을 보존합니다. D1 백업을 운영 DB에 그대로 덮어쓰지 않습니다. 코드 롤백이 스키마를 되돌리지는 않습니다. 0009 이후 복구 관계가 생겼다면 이를 모르는 이전 코드로 운영하지 말고 현재 스키마와 호환되는 수정본을 dry_run으로 배포합니다.
4. 백업 복원이 필요하면 먼저 격리 로컬 DB에서 SQL·FK·적용 이력을 검증합니다. 전체 export는 스키마도 포함하므로 빈 DB에 가져옵니다. 이미 테이블이 있는 DB에 다시 초기 마이그레이션을 적용하지 않습니다. 기존 Free 계정 한도 안에서 별도 복구 DB를 만들 수 있을 때만 다음 원격 절차를 진행합니다. 무료 자격이 없으면 중단합니다.

다음은 복구용 명령 예시이며 이번 작업에서는 실행하지 않았습니다. `RESTORE_SQL`은 검증된 실제 백업으로, `RESTORE_DB`는 새 빈 복구 DB 이름으로 지정합니다. 같은 이름의 기존 DB가 있으면 새 고유 이름을 사용합니다.

```sh
RESTORE_DB=en-card-restore-20260929
RESTORE_SQL=backups/pre-m5-YYYYMMDD-HHMMSS.sql
npx wrangler d1 create "$RESTORE_DB"
npx wrangler d1 execute "$RESTORE_DB" --remote --config wrangler.deploy.jsonc --file "$RESTORE_SQL" --yes
npx wrangler d1 execute "$RESTORE_DB" --remote --config wrangler.deploy.jsonc --command "PRAGMA foreign_key_check; SELECT name FROM d1_migrations ORDER BY id;" --json
```

FK가 비어 있는지, 핵심 테이블 행 수·저장량·sending/unknown·복구 관계가 백업과 일치하는지 비교합니다. 내보내기에 마이그레이션 이력이 없으면 실제 스키마와 원본 이력을 대조하여 복구하기 전까지 `migrations apply`를 실행하지 않습니다. 확인 후 dry_run 설정의 DB 바인딩을 복구 DB 식별자로 바꾸고 아직 적용하지 않은 후속 마이그레이션만 적용합니다. KV 바인딩은 보존한 이미지 namespace를 가리켜야 합니다. 기존 암호화 키가 없으면 기존 토큰을 복호화할 수 없으므로 재연결합니다.

복원된 `sending`은 실제 결과 확인 전 성공·pending으로 바꾸지 않습니다. 만료 후 unknown 처리와 사용자 확인을 거치며, 백업 시점 뒤 이미 보낸 메시지는 오래된 pending 자료에 반영되지 않을 수 있으므로 채팅방·시도 이력을 대조하기 전에는 live를 재개하지 않습니다. 복구된 과거 회차를 일괄 재발송하지 않고, 필요한 카드만 검토하여 새 미래 예약으로 만듭니다. 원본 DB 삭제와 live 재개는 별도 결정이며 백업 성공만으로 진행하지 않습니다.

## 인증과 실패 진단

로그아웃은 세션만 지우며 운영 예약은 유지됩니다. 자동 발송 연결 해제는 모든 예약을 중단하고 암호화 토큰을 삭제합니다. 소유자 ID는 남아 다른 사용자가 재등록하지 못합니다.

OAuth state는 브라우저 바인딩·만료·단일 소비를 검사합니다. 코드·토큰 교환의 응답이 불명확하면 재사용하지 않고 다시 로그인합니다. 리프레시 회전도 잠금과 version으로 보호하며 동시 갱신은 다음 Cron으로 미룹니다. 일반 GET 사용자 조회와 달리 토큰 회전·메시지 전송을 무조건 재시도하지 않습니다.

D1/KV 장애가 생기면 발송 상태와 용량 예약을 먼저 확인합니다. 오류 ID·API 경로·HTTP 상태·카카오 코드·시각을 사용하고 인가 코드·토큰·Secret·OAuth 원문을 로그나 문의에 첨부하지 않습니다. 한도나 제공사 장애는 유료 서비스로 우회하지 않습니다.

연결 권한이 철회되면 미래의 활성 예약도 중단합니다. 재연결 후 원하는 예약을 직접 재개하세요. 이전 인증의 늦은 오류 응답은 새 인증 버전을 덮어쓰지 않습니다. 세션이 만료되면 로그인 화면에서 다시 연결할 수 있습니다. 동일한 dry_run 결과는 매분 새 기록을 쌓거나 갱신하지 않으며 카드·시간·피드가 달라질 때만 기록이 바뀝니다.

### 응답 대기 중 일시정지와 확정 거절

응답을 기다리는 카드는 일시정지 시 `sending`을 보존합니다. 이후 확정된 미접수 응답(제한·인증 거절·실패)이 오면 응답 저장과 동시에 DB의 현재 일시정지 상태를 확인해 `cancelled`로 확정하고 복구 후보를 기록합니다. 원래 호출 결과·시도 횟수·발송 예산은 보존하며 복구·제외를 결정하기 전 기존 예약을 재개할 수 없습니다. 성공은 접수 상태로, 결과 불명은 `unknown`과 수동 확인 보호로 유지합니다.

미결정 후보는 DB에서 한 번에 40건만 읽고, 완료 이력도 40건씩 **완료 이력 더 보기**로 조회합니다. 동률 시각에도 커서에 식별자를 함께 사용해 누락·중복 없이 읽습니다. 오래된 버전에서 이미 누락된 `retry_wait`·`blocked` 건은 현재 버전으로 같은 예약의 일시정지 API를 다시 실행하여 미발송을 취소·등록한 뒤 복구 또는 제외합니다. 과거의 terminal `failed`는 이 절차의 대상이 아니므로 호출 이력을 보존하고 수정한 카드로 새 예약을 준비합니다. `sending`·미해결 `unknown`은 먼저 발송 기록에서 확인합니다. 2026-10-01 현재 운영 DB에는 이 형태의 미등록 건이 0건이므로 운영 데이터 보정은 하지 않았습니다.

### 저장 인증정보 오류의 수동 복구
